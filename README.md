# Лабораторная работа №6: Мониторинг Java-приложения с использованием Prometheus и Grafana

**Дисциплина:** Инструментальные средства проектирования программного обеспечения (ИППРПО)  
**Предметная область:** Музыкальный сервис (Music Streaming Service)  
**Вариант:** 11  
**Индивидуальное задание:** Реализовать и отобразить в Grafana метрики работы музыкального сервиса. Продемонстрировать изменение метрик при успешном воспроизведении и при попытке воспроизвести недоступный трек.

---

## 1. Архитектура решения и полный цикл

В лабораторной работе выстроен полный индустриальный цикл разработки, автоматизации тестирования и мониторинга:

```
Git Repository (ветка main)
     ↓
Jenkins (Pipeline)
     ↓
[Checkout] → [Build] → [Static Analysis (Checkstyle)] → [Test (JUnit 5)] → [Package (JAR)]
     ↓
Application (Java 23 / Micrometer, порт 8081)
     ↓
Metrics Endpoint (http://localhost:8081/metrics)
     ↓ (HTTP Scrape каждые 5 сек)
Prometheus (порт 9090, Target UP)
     ↓ (PromQL-запросы)
Grafana (порт 3000, Data Source = Prometheus)
     ↓
Dashboard: "Music Service Monitoring (ЛР №6, Вариант 11)"
```

## 2. Реализованные метрики (Micrometer + Prometheus)

В проекте реализован класс `by.ipprpo.music.metrics.MetricsManager` на базе `PrometheusMeterRegistry`.

| Метрика | Тип | Описание | Когда изменяется |
| :--- | :--- | :--- | :--- |
| `application_operations_total` | Counter | Общее количество всех операций в системе | При выполнении любой операции (создание, добавление, удаление, воспроизведение) |
| `application_operations_success_total` | Counter | Количество успешно завершенных операций | При успешном выполнении операции |
| `application_operations_error_total` | Counter | Количество операций, завершившихся ошибкой | При возникновении ошибок валидации, отсутствии трека, недоступности |
| **`music_service_playback_success_total`** *(Вариант 11)* | Counter | Количество успешных воспроизведений аудиокомпозиций | При успешном вызове `playTrack()` для доступного трека |
| **`music_service_playback_error_total`** *(Вариант 11)* | Counter | Количество попыток воспроизвести недоступный/отсутствующий трек | При попытке воспроизвести заблокированный трек (`available=false`) или отсутствующий ID |
| `music_service_playback_duration_seconds` | Timer | Длительность выполнения операции воспроизведения | Фиксирует время вызова метода воспроизведения (квантили 0.5, 0.95, 0.99, max) |

## 3. Эндпоинты приложения

Приложение запускает встроенный легковесный HTTP-сервер (`MetricsServer`) на порту **8081** (чтобы исключить конфликт с портом Jenkins 8080):

* **`GET http://localhost:8081/metrics`** — Prometheus Scrape Endpoint (отдает метрики в стандартном текстовом формате Prometheus).
* **`GET http://localhost:8081/`** — интерактивный веб-интерфейс приложения с текущими показателями метрик и кнопками выполнения операций.
* **`GET http://localhost:8081/api/play?playlistId=1&trackId=1`** — успешное воспроизведение доступного трека 1.
* **`GET http://localhost:8081/api/play?playlistId=1&trackId=3`** — попытка воспроизведения недоступного (заблокированного правообладателем) трека 3 (`available=false`).
* **`GET http://localhost:8081/api/play?playlistId=1&trackId=999`** — попытка воспроизведения несуществующего трека.
* **`GET http://localhost:8081/api/simulate`** — пакетная симуляция трафика (5 успешных воспроизведений и 2 ошибки) для наглядной демонстрации на защите.

## 4. Конфигурация Prometheus

* **Файл конфигурации:** `tools/prometheus/prometheus.yml`
* **Адрес веб-интерфейса:** `http://localhost:9090`
* **Раздел Targets:** `http://localhost:9090/targets`

Конфигурация задачи сбора метрик:
```yaml
scrape_configs:
  - job_name: "music-service"
    scrape_interval: 5s
    metrics_path: "/metrics"
    static_configs:
      - targets: ["localhost:8081"]
```

Статус таргета: **`UP`** (Prometheus каждые 5 секунд опрашивает приложение и обновляет Time Series).

## 5. Запросы PromQL

В веб-интерфейсе Prometheus (`http://localhost:9090/graph`) выполняются следующие запросы:

1. **Общее количество операций:**
   ```promql
   application_operations_total
   ```
2. **Количество успешных операций:**
   ```promql
   application_operations_success_total
   ```
3. **Количество ошибок:**
   ```promql
   application_operations_error_total
   ```
4. **Вариант 11 — Успешные воспроизведения:**
   ```promql
   music_service_playback_success_total
   ```
5. **Вариант 11 — Попытки воспроизвести недоступный трек:**
   ```promql
   music_service_playback_error_total
   ```
6. **Скорость выполнения операций (ops/sec):**
   ```promql
   rate(application_operations_total[1m])
   ```
7. **Максимальное время отклика операции воспроизведения:**
   ```promql
   music_service_playback_duration_seconds_max
   ```

## 6. Настройка и Dashboard в Grafana

* **Адрес веб-интерфейса:** `http://localhost:3000`
* **Авторизация:** встроенный анонимный вход с правами администратора (также доступен логин `admin` / пароль `admin`).
* **Data Source:** Prometheus (`http://localhost:9090`), настроен через автоматический provisioning (`tools/grafana/conf/provisioning/datasources/prometheus.yml`).
* **Dashboard:** `"Music Service Monitoring (ЛР №6, Вариант 11)"`, автоматически загружается из `6/grafana_dashboard.json`.
* **Прямая ссылка:** `http://localhost:3000/d/music-service-monitoring`

### Панели дашборда (7 panels):
1. **Total Operations** *(Stat)* — отображает общее число операций (`application_operations_total`).
2. **Successful Operations** *(Stat, зеленый)* — число успешных операций (`application_operations_success_total`).
3. **Operation Errors** *(Stat, красный)* — число ошибок (`application_operations_error_total`).
4. **Playback Status (Вариант 11)** *(Gauge)* — соотношение успешных и ошибочных воспроизведений.
5. **Operations Over Time** *(Time Series)* — график динамики всех, успешных и ошибочных операций во времени.
6. **Music Playback Metrics (Вариант 11)** *(Time Series)* — отдельный график динамики успешных воспроизведений и попыток доступа к недоступным трекам.
7. **Operation Duration** *(Time Series / Bars)* — время выполнения операций воспроизведения (`music_service_playback_duration_seconds_max`).

## 7. Проведение эксперимента (Part 9)

Для демонстрации работы мониторинга в проект включен скрипт симуляции `simulate_traffic.py` (или `simulate_traffic.bat`).

### Сценарий эксперимента:
1. Выполняются штатные операции (воспроизведение трека 1).
2. Выполняются проблемные операции (попытка воспроизвести заблокированный трек 3 и несуществующий трек 999).
3. Фиксируется состояние метрик ДО и ПОСЛЕ Scrape.

### Результаты измерений:
| Показатель | Значение ДО | Значение ПОСЛЕ | Изменение ($\Delta$) | Причина изменения |
| :--- | :---: | :---: | :---: | :--- |
| **Всего операций** | 15 | 21 | **+6** | Выполнено 6 новых запросов к сервису |
| **Успешные операции** | 11 | 14 | **+3** | 3 успешных воспроизведения трека 1 |
| **Ошибки операций** | 4 | 7 | **+3** | 2 отказа по недоступному треку 3 + 1 по треку 999 |
| **Успешных воспроизведений** | 7 | 10 | **+3** | Зафиксировано 3 успешных проигрывания аудио |
| **Ошибок воспроизведения** | 4 | 7 | **+3** | Зафиксировано 3 попытки работы с недоступными треками |

**Вывод эксперимента:** метрики приложения не захардкожены, они в реальном времени отражают внутреннее состояние предметной области и немедленно транслируются через Prometheus в Grafana.

## 8. Сравнение Logging и Monitoring

| Критерий | Logging (ЛР №5) | Monitoring (ЛР №6) |
| :--- | :--- | :--- |
| **Формат данных** | Текстовые сообщения о единичных событиях | Числовые временные ряды (Time Series) |
| **Основной инструмент** | SLF4J + Logback, консоль, лог-файлы | Micrometer, Prometheus, PromQL, Grafana |
| **Назначение** | Детальный анализ причин конкретного сбоя (post-mortem) | Наблюдение за трендами, общим состоянием системы и нагрузкой |
| **Пример** | `WARN PlaylistService - трек 'Radioactive' (ID=3) недоступен` | `music_service_playback_error_total = 7` |
| **Хранение** | Объемные текстовые файлы/Elasticsearch | Компактные числовые выборки со временными метками |
| **Взаимодополняемость** | Мониторинг сигнализирует *что* и *когда* пошло не так (всплеск ошибок); логи объясняют *почему* (детали запроса, stack trace). |

## 10. Ответы на контрольные вопросы к защите ЛР №6

1. **Что такое Monitoring?**  
   *Мониторинг* — это непрерывный процесс сбора, хранения, анализа и визуализации количественных показателей (метрик), отражающих состояние, производительность и доступность работающего программного обеспечения в режиме реального времени.

2. **Что такое Metric?**  
   *Метрика* — это числовой показатель с именем, временной меткой и опциональным набором меток (labels/tags), характеризующий определенный аспект поведения системы (например, `application_operations_total = 21`).

3. **Чем Monitoring отличается от Logging?**  
   *Logging* фиксирует дискретные текстовые события с подробностями контекста (что конкретно произошло и почему). *Monitoring* агрегирует числовые показатели во времени, позволяя строить графики, отслеживать динамику, определять тренды и оперативно выявлять аномалии без чтения миллионов строк логов.

4. **Чем Monitoring отличается от Static Analysis?**  
   *Static Analysis* выполняется на этапе сборки без запуска кода (анализирует текст программы на соответствие стилю и потенциальные дефекты). *Monitoring* наблюдает за уже запущенным и функционирующим приложением во время его реальной работы.

5. **Что такое Prometheus?**  
   *Prometheus* — это распределенная система мониторинга с открытым исходным кодом, предназначенная для сбора метрик по модели pull (scrape) через HTTP, их эффективного сохранения в базу данных временных рядов (TSDB) и обработки запросов на языке PromQL.

6. **Как Prometheus получает метрики от приложения?**  
   Prometheus использует модель **Pull (Scrape)**: он периодически отправляет HTTP GET запросы на сконфигурированный endpoint приложения (например, `http://localhost:8081/metrics`) и парсит текстовый ответ формата OpenMetrics/Prometheus.

7. **Что такое Scrape?**  
   *Scrape (скрейпинг)* — это единичный процесс опроса сервисом Prometheus заданного Target по HTTP для считывания текущих значений метрик.

8. **Что такое Target в Prometheus?**  
   *Target (цель)* — это описание сетевого адреса и эндпоинта контролируемого сервиса (например, `localhost:8081`), параметры опроса (интервал, таймаут) и метки, присваиваемые собранным метрикам.

9. **Что такое Time Series?**  
   *Time Series (временной ряд)* — это последовательность измерений числового значения метрики, упорядоченных по времени, однозначно идентифицируемая именем метрики и набором пар ключ-значение (labels).

10. **Для чего используется Micrometer?**  
    *Micrometer* — это фасад для сбора метрик в Java (аналог SLF4J для логирования). Он позволяет разработчику объявлять метрики (Counter, Gauge, Timer) через универсальный API, не привязываясь к конкретной системе мониторинга, а затем экспортировать их в нужный формат (Prometheus, Influx, Datadog и др.).

11. **Что такое Prometheus Registry?**  
    *Prometheus Registry (`PrometheusMeterRegistry`)* — это специализированная реализация реестра метрик Micrometer, которая хранит все зарегистрированные метрики и форматирует их в текстовый протокол, понятный Prometheus, при вызове метода `scrape()`.

12. **Что такое endpoint метрик?**  
    *Endpoint метрик* — это сетевой URL-адрес приложения (обычно `/metrics`), при обращении к которому приложение отдает текущие показатели всех зарегистрированных метрик.

13. **Что такое PromQL?**  
    *PromQL (Prometheus Query Language)* — встроенный функциональный язык запросов Prometheus, позволяющий фильтровать временные ряды по меткам, вычислять агрегаты (`sum`, `avg`), темпы роста (`rate`, `increase`) и математические операции.

14. **Что такое Grafana?**  
    *Grafana* — это ведущая платформа визуализации и аналитики с открытым исходным кодом, позволяющая строить интерактивные панели и графики на основе данных из различных источников (Prometheus, PostgreSQL, Elasticsearch и др.).

15. **Чем Grafana отличается от Prometheus?**  
    Prometheus собирает и хранит данные, выполняет вычисления. Grafana сама не хранит метрики приложений, она подключается к Prometheus как к Data Source и отвечает за удобный, гибкий графический интерфейс (Dashboards).

16. **Что такое Data Source в Grafana?**  
    *Data Source* — это сконфигурированное подключение к источнику данных (в нашем случае Prometheus по адресу `http://localhost:9090`), из которого Grafana запрашивает информацию для построения графиков.

17. **Что такое Dashboard?**  
    *Dashboard (дашборд)* — это визуальная панель мониторинга, объединяющая набор графиков, индикаторов и счетчиков, предоставляющая целостную картину состояния системы в одном окне.

18. **Что такое Panel?**  
    *Panel (панель)* — это отдельный визуальный блок внутри дашборда, настроенный на отображение конкретного PromQL-запроса в виде графика (Time Series), отдельного числа (Stat), спидометра (Gauge), круговой диаграммы (Pie chart) или таблицы.

19. **Какие данные можно отображать на Dashboard?**  
    Числовые показатели счетчиков (Counters), мгновенные значения (Gauges), графики темпов изменения запросов во времени, гистограммы времени отклика, статусы доступности сервисов, распределение ошибок по типам.

20. **Как проверить, что Prometheus получает метрики приложения?**  
    1. Открыть раздел **Targets** в Prometheus (`http://localhost:9090/targets`) — статус таргета должен быть **`UP`** (зеленый).
    2. В поле запроса на вкладке **Graph** ввести имя метрики (например, `application_operations_total`) и нажать **Execute** — должно отобразиться актуальное числовое значение.

21. **Что произойдет с метрикой количества операций после выполнения новой операции?**  
    Значение счетчика `Counter` увеличится на 1 (`application_operations_total`). При следующем скрейпе Prometheus зафиксирует новое значение, и на графике Grafana отобразится восходящая ступенька.

22. **Что произойдет с метрикой ошибок после ошибочной операции?**  
    Счетчик ошибок `application_operations_error_total` и специализированная метрика `music_service_playback_error_total` увеличатся на 1, а счетчик успешных операций останется неизменным.

23. **Почему Logging и Monitoring не заменяют друг друга?**  
    Потому что они решают разные задачи на разных масштабах: мониторинг сообщает о проблеме на макро-уровне ("выросла частота отказов до 15%"), а логи дают микро-уровень ("User 1 attempted to play track 3 with available=false: TrackUnavailableException").

24. **Какую роль Monitoring выполняет в промышленной разработке?**  
    Мониторинг обеспечивает соблюдение SLA/SLO, позволяет проактивно обнаруживать сбои и деградацию производительности до жалоб пользователей, помогает планировать масштабирование ресурсов и оценивать надежность релизов при непрерывной доставке (CI/CD).

25. **Что произойдет, если приложение недоступно для Prometheus?**  
    Prometheus не сможет выполнить Scrape: в TSDB будет записано значение `up{job="music-service"} = 0`, статус таргета сменится на **`DOWN`**, а на графиках метрик приложения появятся разрывы (отсутствие новых точек).

26. **Что необходимо проверить, если Target имеет статус DOWN?**  
    - Запущен ли процесс Java-приложения.
    - Доступен ли сетевой порт (8081) и не занят ли он другим процессом.
    - Корректен ли URL-адрес (`/metrics`) и возвращает ли он HTTP 200 OK при прямом запросе через браузер или `curl`.
    - Нет ли блокировок со стороны межсетевого экрана (firewall).
    - Правильно ли указан адрес в `prometheus.yml`.

27. **Как убедиться, что Dashboard отображает реальные данные приложения?**  
    Выполнить в приложении операцию (например, воспроизвести доступный трек через веб-интерфейс или API `/api/play?playlistId=1&trackId=1`), подождать интервал опроса (5 секунд) и убедиться, что число на панели *Successful Operations* и график *Music Playback Metrics* синхронно увеличились ровно на 1.
